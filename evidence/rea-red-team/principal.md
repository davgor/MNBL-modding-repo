## 1. Compatibility recognizes version labels, not the artifact that supplied the contracts

**Observed limitation.** `UI/WorldSetupScreen.cs:167-179` constructs a host profile by taking the installed three-component NavalDLC release and, when it matches, substituting the embedded lock's complete `v1.2.8.119303` value. It does not measure that build from NavalDLC. `Campaign/GeneratedPatches.cs:106-114` checks the game's complete version but only NavalDLC Major/Minor/Revision. `WorldSetupScreen.cs:139-159` hashes the generator executables, not the game assemblies. `BundleHost` supplies R01-R10 as a constant capability list.

The repository already has exact assembly hashes in `config/runtime-api-lock.json`; `CampaignBootstrap/PeriodicSpatialTable.cs:156` also records the audited assemblies for an offline check. A source search found no runtime consumer of `ScannedAssemblies`, and the runtime lock consumer in `BundleHost` reads only its `navalVersion`. Existing patch target/signature/count checks remain useful; this review does not claim they are absent.

**Executed proof.** The coordinator ran `powershell -NoProfile -File evidence/rea-red-team/principal-repro.ps1`. It extracts and compiles the unchanged bodies of `RequireInstalledVersion`, `InstalledVersions`, and `BundleHost`, with controlled version-provider stubs and the real embedded lock. Results are in `principal-repro-results.txt`: 1.2.8 is accepted and becomes 1.2.8.119303; 1.2.9 is refused; identical version metadata is indistinguishable regardless of the scenario's artifact label. The control assertions passed. All three profile calls advertise R01-R10.

**Important proof boundary:** the scenario named `changed_dll_same_release` does NOT modify or load a DLL. It proves these methods have no artifact-identity input; it does not prove a changed assembly would survive every later patch preflight or run the game successfully. `artifactBytesConsulted=false` is harness annotation, not a runtime trace. The installed binaries actually checked by the coordinator match the captured lock (`installed-inputs.json`). Treat this as future drift prevention, not a blocker caused by today's installation.

**Action for Claude / stronger Harmony research.** Add a once-per-process measured host receipt, using actual loaded assembly locations and SHA-256/MVID plus active patch owners. Bind the specific inspected method signatures, raw CIL hashes and exception-region contracts to that receipt. Reuse the existing lock first. REA can produce the static side and a differential report when a game update changes the bytes; the game-side probe should verify the runtime side before campaign mutation. Distinguish supported capability declarations from observed capability checks. A changed method body with unchanged release metadata must invalidate the relevant acceptance receipt. Do not use REA's normalized instruction hash alone as a semantic-equivalence proof: tokens are build-local and its stated limitations include incomplete control-flow commitment.

**First acceptance check:** keep public version metadata fixed, alter an owned fixture's targeted method body, and verify the new identity gate refuses it before applying patches. A second fixture changing only unrelated code should be handled by an explicit review/update path rather than quietly called equivalent. Never mutate the installed game for this check.

## 2. REA-backed replay oracle: compare actual object identities and edges

**Observed existing boundary.** `Campaign/MBObjectStore.cs:97-102,127-143` projects runtime objects to `(StringId, IsReady)`. `Campaign/CampaignObjectRegistry.cs:173` intentionally accepts a saved temporary type by campaign-list membership during replay. `:213-215` checks settlement membership by StringId. This proves the stated registration/list predicates; those values cannot additionally prove that a settlement, its owner, its clan and a replayed XML reference point to the same instances. No duplicate instance or broken ownership edge was demonstrated here.

**Why the installed code makes this a valuable oracle.** REA inspection of `CampaignObjectManager` shows `InitializeOnLoad` takes the Settlement list from MBObjectManager but rebuilds faction/party indexes from saved lists and invokes `InitializeManagerObjectLists`. Supplemental, execution-free Cecil IL confirms the latter computes next sub-IDs from `GetMaxObjectSubId`. REA's MBObjectBase methods include both `StringId` and `Id`; supplemental IL of `OnBeforeLoad` checks the object's registered state and calls `TryRegisterObjectWithoutInitialization(this)`. Registry membership, runtime instance identity and game object ID are related but distinct facts.

**Action / first proof.** Extend the existing two-world load matrix with a read-only identity oracle at four checkpoints: before XML replay, after replay, after the engine removes non-ready objects, and after load completion. For permanent types record StringId, MBGUID/Id, phase-scoped reference identity and readiness. For temporary types compare the saved campaign objects and all relevant live edges (settlement owner, hero clan, clan kingdom, party component owner), not a presumed XML lookup alone. Re-save and cold-load, and alternate world A / world B / A in one process. Across processes compare game IDs and graph edges, never CLR reference addresses. Use a deliberate same-StringId/wrong-instance fixture as the oracle's positive control. This strengthens the existing MMR-49 acceptance plan; it does not claim that ordinary load routing was already promised or implemented.

This is a useful prerequisite to more ambitious generated dynasties, evolving factions and persistent world events: those additions increase the saved object graph, so silent identity substitution becomes much more expensive to diagnose.

## Independent peer check

For the gamer lens, independently confirmed that `World/GeneratedClimateSystem.cs:104,112-114` requires twelve snow months then reduces them to a per-cell maximum; `:194` samples that maximum plus IceCap. This discards monthly phase in the generated field; it does not mean the game's final weather never changes with time.
